第一章 · llama-shell 使用说明Llama-Shell Guide

1.1界面布局与按钮功能

程序主窗口分为三块：顶部按钮栏、左侧模型栏（模型列表 + 上下文预设）和右侧主区（参数面板、GPU/内存监控条、状态栏、命令预览）。顶部共 9 个按钮：

按钮作用
加载模型用当前参数启动 llama-server 并加载左侧选中的模型，即"启动"。加载成功后状态栏会显示运行状态，可通过状态栏的「网页运行」打开内置 WebUI。
卸载模型停止 llama-server 进程，释放显存与内存，即"停止"。
重启模型先卸载再加载。改完参数后点它即可让新参数生效。
保存参数把当前模型的所有参数保存到 models_config.json，下次打开自动恢复。
重置参数把当前模型恢复到第一次被发现时的默认参数。
打开日志打开 logs 目录里的运行日志，报错时先看这里。
官网打开 llama.cpp 的 GitHub 项目主页。
更新检查并安装 llama.cpp 新版本，详见 1.4。
帮助打开本帮助页面。地址由 config.json 的 help_url 决定，详见 1.5。
💡 右侧底部的命令预览实时显示将执行的完整命令行，点「复制」可以直接拿到别处使用；启动前看一眼，就知道程序到底要做什么。

1.2模型管理与上下文预设

模型列表自动扫描模型目录（默认是程序所在目录的上一级，也就是存放 .gguf 文件的目录）里的全部 .gguf 模型，点击即可切换。把新模型下载到该目录后，点列表下方的刷新按钮就能看到。

上下文预设提供 4k / 8k / 16k / 32k / 64k 五档，一键设置上下文长度（--ctx-size）。上下文越大越占显存，选模型能"装得下"的最大档位即可；不清楚什么是上下文，先看 2.0 入门概念。

⚠️ 每个模型的参数互相独立，切换模型后会自动载入该模型上次保存的参数。

1.3参数面板与悬停说明

参数面板按 llama-server --help 的原始分组分成多个标签页：服务器、模型、性能、采样、推理、投机、多模态、日志、高级，另有版本更新后自动补齐的「自动补齐」页。

  • 参数名按 help 原样显示 flag（如 --n-gpu-layers），不做翻译，保证和官方文档、命令行教程一一对应。
  • 把鼠标悬停在参数行上，会弹出中文提示：参数含义、类型、默认值和可选值。
  • 右侧命令预览实时反映你的每一处改动，所见即所得。

1.4启动与更新流程

启动程序

双击 启动.vbs 即可（内部以 pythonw main.py 运行，不弹黑窗）。程序启动时会自动读取 config.json 与 models_config.json，并与当前 llama-server --help 对账参数表。

更新 llama.cpp

  1. 点顶部「更新」按钮，程序通过 winget 查询最新版本；
  2. 发现新版本后弹出确认框，由你决定是否升级；
  3. 确认后后台执行 winget upgrade（新版本体积约 200MB，请耐心等待）；
  4. 升级成功后程序弹窗提示并自动重启；
  5. 重启后自动按新版 --help 对账参数表——新增参数会出现在「自动补齐」分组里，无需手动同步。
⚠️ 如果你在命令行里手动执行 winget upgrade，参数表不会立刻同步——重启一次本程序即可自动完成对账。

1.6常见问题

参数太多，不知道什么意思怎么办？把鼠标悬停在参数行上看中文提示；想看更完整的解释与影响，去 2.2 全参数参考。参数说明以程序内悬停提示为准——程序更新后悬停内容会跟随最新版本，本页静态内容可能略有滞后。
手动 winget 升级后参数会和界面脱节吗？不会。参数表在程序每次启动时自动与 llama-server --help 对账，升级完重启一次程序即可。
模型应该放在哪里？放在 config.json 里 models_dir 指向的目录（默认是程序目录的上一级），扩展名必须是 .gguf。
点「帮助」没反应？说明 help_url 指向的本地文件不存在（默认应为程序目录下的 help/index.html），或网络地址不可达。程序会弹出警告提示；部署在线站点后把 help_url 改成完整网址即可。
加载模型时报显存不足 / OOM？三选一：降低 GPU 层数（-ngl）、调小上下文（-c）、换更小量化等级的模型文件。原理见 2.1 常用参数精讲。
端口被占用，启动失败？改「服务器」分组里的 --port（默认 8080）为其他未被占用的端口，再重启模型。

第二章 · llama.cpp 通用知识llama.cpp Basics

2.0入门概念：看懂大模型的"黑话"

🧩 Token：模型眼里的"字"

模型不是按"字"处理文字的，而是按 token——一段模型词表里的基本单元。一个英文单词约等于 1~2 个 token，一个汉字通常是 1 个 token 左右。所有和"数量"有关的参数（上下文长度、预测长度、批大小）单位都是 token。

🪟 上下文窗口（Context）：模型一次能"记住"多少内容

上下文长度（--ctx-size，-c）决定一次对话中模型能同时看见的 token 总量——包括你的提问、它已经生成的内容以及系统提示。超出了就"记不住"最早的内容。4k≈能读几页文档，32k≈能读一篇长报告，128k 以上则接近整本书。上下文越大，显存占用越高。

📦 量化与 GGUF：又小又能跑的模型文件

GGUF 是 llama.cpp 使用的模型文件格式，所有 .gguf 文件都是它。量化（Quantization）是把模型权重从高精度小数压缩成低精度整数的过程——模型能力几乎不损失，文件体积和显存占用大幅下降。

看懂文件名：Qwen3-8B-Q4_K_M.gguf = 模型名 Qwen3、参数量 8B（80 亿）、量化格式 Q4_K_M。量化等级从粗到细大致是：

等级每权重约占用特点
Q2/Q32~3.5 bit体积最小，质量下降明显，仅极限压缩时使用
Q4_K_M≈4.8 bit最常用的平衡档，推荐默认选择
Q5_K_M / Q6_K5.5~6.6 bit更接近原版质量，体积约大 20%~40%
Q8_0≈8.5 bit几乎无损，体积接近原始模型的一半
F1616 bit原始精度，一般只用于继续训练

估算显存：8B 模型的 Q4_K_M 约 5GB，加上上下文缓存的开销，一块 8GB 显存的显卡即可运行。

🎮 GPU Offload：把模型"搬"进显卡

大模型由很多层（layer）组成。GPU 卸载（--n-gpu-layers，-ngl）指把其中 N 层放进显存里用显卡计算——显卡算得快，但显存有限；放不下的层留在 CPU/内存里慢慢算。-ngl 999（或 all）表示"全部塞进显卡"，是最常用的写法；显存不够时程序会自动减层或直接报错，此时调小数字即可。

🎲 采样：为什么同一句话每次回答都不一样

模型每一步其实是在给"下一个 token 的所有候选"打概率分，采样就是从这个榜单里挑一个的过程：

  • 温度（--temp）：控制"敢不敢冒险"。低温（0.1~0.5）回答稳定保守，适合写代码、做问答；高温（0.8~1.2+）回答更有创意、更发散，适合写小说，但太低会显得呆板、太高会语无伦次。
  • Top-P（--top-p）：只从"累计概率前 P"的候选里挑。0.9 表示只考虑加起来占 90% 概率的那批词，把长尾胡话过滤掉。
  • Top-K（--top-k）：只从概率最高的 K 个候选里挑，是 Top-P 的"按个数"版本。

日常使用：--temp 0.7 --top-p 0.9 是稳妥的起点；想要更稳就降温，想要更"放飞"就升温。

2.1常用参数精讲：设大设小会怎样

以下是最常被调动的参数。每张卡片解释"它是什么、为什么存在、调大调小各有什么影响"。

-ngl / --n-gpu-layers — GPU 卸载层数

决定多少层模型权重放进显存。这是对速度影响最大的单一参数。

显存占用↑、生成速度↑（越多层走显卡）。设 999 或 auto 让程序自动装满。
显存占用↓，但更多层落到 CPU 上，速度明显变慢。显存不够 / OOM 时往下调。

-c / --ctx-size — 上下文长度

一次对话能容纳的 token 总量，直接决定显存中 KV 缓存的大小。

能"记住"的对话/文档更长，但显存占用显著增加（与 token 数近似成正比）。
省显存，但长对话会被截断、长文档读不完。日常 8k~32k 足够。

-t / --threads — CPU 线程数

模型跑在 CPU 上的部分用几个线程计算。一般等于物理核心数（不含超线程）。

超过物理核心数后收益趋零甚至变慢（超线程争抢）。
CPU 部分变慢；但留出核心给系统和其他程序更流畅。

-b / --batch-size 与 -ub / --ubatch-size — 批大小

模型一次"咀嚼"多少 token：逻辑批（-b）是上限，物理批（-ub）是实际每步的计算粒度。默认 2048 / 512 通常不用动。

喂长提示词（prefill）更快，但显存峰值更高。
省显存，长提示处理变慢。显存紧张时先把 -ub 降到 256 或 128。

-n / --predict — 预测 token 数

单次回复最多生成多少 token。-1 表示不限制，由上下文或停止符决定结束。

允许更长的单次输出（长文写作可设大或 -1）。
回复被截短，但可以避免模型"刹不住车"刷屏。

--temp — 温度（随机性）

见 2.0 采样概念。默认 0.8。

回答更有创意、多样，但可能跑偏、胡说（>1.2 明显失控）。
回答稳定、准确、可复现；太低（<0.3）会呆板重复。写代码建议 0.2~0.6，写小说 0.8~1.1。

--top-p — 核采样阈值

只从累计概率前 P 的候选中采样。默认 0.95。

保留更多低概率候选，输出更丰富也更冒险。
输出更保守；过低（<0.5）会只在几个固定词里打转。

--top-k — 候选数上限

只在概率最高的 K 个 token 里采样。默认 40，设 0 表示关闭。

候选更多、更发散。
更收敛；配合温度使用，一般不需要大动。

-np / --parallel — 并行槽位数

服务器同时处理几个请求，每个请求占用一个"槽位"和一份 KV 缓存。

能同时服务多人/多任务，但上下文会被均分、显存成倍增长。
单人使用保持 1 即可，上下文与显存都归一个请求独享。

第三章 · 常见需求的解决办法How-To Recipes

按"你想要什么"组织的实用配方，每个都给出可直接在参数面板里填写的参数组合。开始前建议先读 2.0 入门概念 理解基本原理。

3.1加大上下文并保留精度（长文本/长对话）

需求：想让模型一次读更多内容（长文档、长篇小说、多轮长对话），但显存不允许直接把 --ctx-size 拉满。

背景：上下文的显存开销主要来自 KV 缓存——它默认以 f16 精度保存，随上下文长度线性增长，长上下文时甚至比模型本身还占显存。所以省显存的正确姿势不是降模型精度，而是降缓存精度。

参数推荐值作用
--ctx-size（-c）按需，如 32768 / 65536上下文长度。按实际需要设置，不要"以防万一"白留显存。
--flash-attnon（新版默认 auto）Flash Attention：降低注意力计算与显存开销，且是 KV 量化的前提。老显卡（GTX 10 系等）不支持时去掉。
--cache-type-kq8_0K 缓存量化为 8bit，缓存体积减半，质量损失实际可忽略，是公认的"免费午餐"。
--cache-type-vq8_0V 缓存同上；必须与 Flash Attention 同时开启。
💡 标准组合：--ctx-size 65536 --flash-attn on --cache-type-k q8_0 --cache-type-v q8_0。显存仍不够时，可把缓存再降到 q4_0（再省约一半，但长文本下质量损失开始可测）；还可以用 --fit（默认 on）让程序自动调整参数适配显存。实测参考：32GB 显卡上 128K 上下文，f16 缓存约需 12GB，q8_0 量化后约 6GB——不量化基本装不下。
⚠️ 若长提示时首字特别慢甚至 OOM：多半是 KV 缓存装不下或没开 Flash Attention（无 FA 时预填计算量随长度平方增长）。按上表组合设置即可；确实不需要超长上下文时，把 -c 降回来才是最直接的解药。

3.2运行超出显存的更大模型

需求：模型文件太大，显存装不下整只，但又不想完全跑 CPU。

思路一：换更低量化等级

同等参数量下 Q4_K_M → Q3_K_M / IQ4 体积再降约 20%~30%。优先降量化而不是砍层数——量化均匀作用于全部权重，而部分卸载会让一半权重走慢速内存。

思路二：MoE 模型 —— 专家留 CPU（强烈推荐）

DeepSeek、Qwen3-MoE、GLM、Kimi 等混合专家（MoE）模型的每个 token 只激活少部分专家权重，把"大多数时间闲置"的专家权重留在内存、注意力层留在显卡，能在小显存上跑动超大模型且速度可观：

参数用法
--cpu-moe全部专家权重留 CPU。最简单的"先让它跑起来"，显存占用最小。
--n-cpu-moe N只有前 N 层的专家留 CPU（N 越小越吃显存、越快）。调法：先 --cpu-moe 确认能加载，再换 --n-cpu-moe 从大往小试（如 40 → 30 → 26…），直到 OOM 后退一档。
--override-tensor更细粒度：用正则指定哪些张量留 CPU，如 ".ffn_.*_exps.=CPU"（等价于全专家留 CPU）。进阶玩法。
-ngl与上面配合，保持 999/auto，让注意力层尽量进显卡。
💡 经验参考：41GB 的 MoE 模型在 24GB 显存上约 --n-cpu-moe 26，16GB 显存约 36。此时瓶颈变成内存带宽——DDR5 双通道比 DDR4 明显更快，生成速度通常仍能有 20~40 tok/s。

思路三：稠密模型 —— 部分 FFN 层留 CPU

非 MoE 模型可用 --override-tensor 把指定层的 FFN 张量挪到 CPU，而注意力与 KV 缓存保持在显卡：-ngl 999 --override-tensor "blk\\.(0|1|2|3)\\.ffn_.*=CPU"（把第 0~3 层的 FFN 留在 CPU，层数按显存试出来）。逐层往显卡搬，搬不动为止。

思路四：多显卡

--split-mode layer（默认）按层分给多卡；--tensor-split 3,1 按 3:1 比例分配显存占用；-sm row 按行切分（需要卡间高速互联，配合 Flash Attention）。

3.3提升生成与首字速度

按收益从大到小逐项检查：

  1. 确认模型全进显卡：-ngl 999 或 auto。哪怕只留几层在 CPU，速度也会明显掉。看监控条确认显存装得下。
  2. 开 Flash Attention：--flash-attn on（RTX 30 系及以后支持良好，约提速 15%~20%；不支持会启动报错，删掉即可）。
  3. 别白留上下文：生成速度随上下文增长而下降（每生成一个 token 都要读全部 KV 缓存）。50 tok/s @1K 掉到 10 tok/s @64K 是正常现象，不是 bug——不需要就把 -c 调小。
  4. CPU 线程数：有层在 CPU 时，-t 设为物理核心数（不含超线程）。
  5. 批大小：喂长提示词慢时加大 -ub（如 1024）；显存紧张时减小。
  6. 量化缓存：--cache-type-k/v q8_0 同时减少每步读取量，对长上下文提速也有帮助。
💡 想量化对比效果，可以在命令行用 llama-bench（pp 行=首字延迟，tg 行=生成速度）做前后对照；GUI 里则直接看监控条与体感。

3.4多人/多任务同时使用

需求：几个应用（或几个人）同时调用同一个服务。

参数推荐值说明
--parallel（-np）2~4并行槽位数。上下文会被均分：总上下文 32k、4 槽位 = 每请求 8k。显存相应增加。
-c总上下文记得按"单请求需要 × 槽位数"设置总量。
--cont-batching默认开启连续批处理，多请求自动合并计算，一般不用动（关掉用 --no-cont-batching）。
💡 实测参考：单卡从 1 并发开到 4~8 并发，总吞吐能翻 3~5 倍，单请求延迟只增加几毫秒；并发开到显存吃满后延迟翻倍，就得不偿失了。4~8 是甜区。单人使用保持 1，把全部上下文留给一个请求。

3.5接入第三方软件（OpenAI 兼容 API）

llama-server 内置 OpenAI 兼容接口：启动模型后，任何支持"OpenAI API 格式"的软件（翻译插件、写作工具、代码助手、沉浸式翻译、SillyTavern 等）都能直连：

--port默认 8080端口，冲突时换一个。

3.6输出乱码 / 重复 / 模板异常

症状：回复前言不搭后语、满屏重复、或出现奇怪的括号标签（如 <|im_start|> 原样输出）。

  • 对话模板不对：GGUF 内置了模板，但个别微调模型没写对。在「模型/服务器」相关分组里用 --chat-template 手动指定（如 chatml、qwen 等预设名），或加 --jinja 改用模型自带的 Jinja 模板（更接近官方行为）。
  • 温度太低/太高：复读机式的死循环重复，试着升一点 --temp、加 --repeat-penalty（默认 1.0，设 1.1 左右抑制重复）。
  • 上下文溢出：对话太长超出 -c，早期内容被截断导致"失忆"。加大上下文（见 3.1）或开新对话。
  • 量化太狠：Q2/Q3 量化的小参数模型本来就语无伦次，换 Q4_K_M 以上再判断是不是参数问题。

3.7显存不足（OOM）排查速查

按顺序做，每做一步重试加载：

  1. 调小上下文 -c（KV 缓存往往是显存大头）；
  2. KV 缓存量化：--flash-attn on --cache-type-k q8_0 --cache-type-v q8_0（见 3.1）；
  3. MoE 模型：--cpu-moe 先跑起来，再逐步改 --n-cpu-moe 往回搬（见 3.2）；
  4. 调小物理批 -ub 256（计算缓冲区变小）；
  5. 降低 GPU 层数 -ngl；
  6. 换更低量化等级的模型文件（Q4_K_M → Q3_K_M）或更小参数量的模型。
